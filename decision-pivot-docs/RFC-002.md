# RFC-002 — Atlas Evolution Blueprint (Part I)

**Status:** Draft v1.0

**Depends On:** RFC-001 — Atlas Product Constitution

---

# 1. Executive Summary

RFC-001 defines **why Atlas exists**.

RFC-002 defines **how Atlas evolves** from its current implementation into the product described by the Constitution.

Atlas already possesses a mature technical foundation:

* Workspace support
* GitHub Context Provider
* LangGraph Research Pipeline
* Corrective RAG
* Decision Records
* Comparison Engine
* Organizational Memory
* Export Engine
* Authentication
* Observability

The objective of this RFC is **not** to redesign these systems.

Instead, the objective is to reorganize them into a coherent Engineering Workspace centered around engineering thinking rather than isolated research sessions.

This RFC follows one guiding principle:

> Preserve existing engineering investment while improving product organization.

---

# 2. Current Atlas (As-Is)

Today's Atlas is fundamentally a **Research-Centric Platform**.

Current user flow:

```text
Workspace

↓

Research

↓

Memory

↓

Recommendation

↓

Decision Record

↓

Export
```

The backend architecture is strong.

The product architecture is fragmented.

Capabilities exist independently rather than contributing to a unified engineering workflow.

Examples:

* GitHub Context Provider exists separately.
* Decision Records exist separately.
* Comparisons exist separately.
* Memory exists separately.

Although technically connected, they are not perceived as one cohesive experience by the user.

# 4. Current Problems

The engineering implementation is ahead of the product model.

The platform currently organizes work around:

Research Sessions.

Engineers do not naturally think in Research Sessions.

Engineers think in projects, goals, and initiatives.

As a result:

Research feels disconnected.

Decision history lacks broader context.

Repository context feels separate.

Memory appears as an implementation detail instead of organizational knowledge.

The backend is cohesive.

The product experience is not.

---

Future philosophy:

# 6. Evolution Principles

Every architectural decision in this RFC follows six principles.

## Preserve Existing Investment

Existing services should be reused whenever possible.

Refactoring is preferred over replacement.

---

## Workspace First

Every object belongs to a workspace.

Workspace isolation becomes the highest ownership boundary.

---

## Engineering Thinking First

Atlas optimizes engineering thinking.

Not AI conversations.

Not prompt history.

---

## Context Before Intelligence

Repository context

*

Workspace knowledge

*

Previous decisions

↓

produce better research.

Context gathering should precede AI reasoning.

---

## Decisions Are Assets

Research expires.

Technology changes.

Engineering decisions remain valuable because they preserve reasoning.

Atlas treats decisions as long-lived organizational assets.

---

## Knowledge Compounds

Every interaction should strengthen future interactions.

The workspace becomes progressively more intelligent over time.

# 8. Domain Evolution

## Workspace

Current:

Container for user data.

Future:

Permanent engineering environment.

No structural redesign required.

Only expanded responsibilities.

---

## Initiative (New)

Current:

Does not exist.

Future:

Primary engineering object.

Everything engineers do belongs to an Initiative.

This replaces isolated research sessions as the center of engineering work.

---

## Exploration (New)

Current:

Implicitly exists inside research prompts.

Future:

Explicit engineering thinking.

Exploration captures:

* ideas
* assumptions
* constraints
* unknowns
* hypotheses

before formal research begins.

---

## Research

Current:

Primary product object.

Future:

Supporting capability.

Research validates engineering thinking.

It no longer represents the product itself.

---

## Decision

Current:

Standalone artifact.

Future:

Outcome of an Initiative.

Every Decision inherits context from:

Workspace

↓

Initiative

↓

Research

↓

Repository Intelligence

making it significantly richer.

---

## Knowledge

Current:

Memory implementation.

Future:

Visible organizational intelligence.

Knowledge becomes a first-class product capability rather than an invisible backend service.

---

## Repository Intelligence

Current:

GitHub Context Provider.

Future:

Engineering context engine.

Every Exploration, Research session, and Decision automatically benefits from repository understanding.

* Corrective RAG

---

# Closing Statement

Atlas is not undergoing a technical rewrite.

It is undergoing a product evolution.

The platform already contains the technical capabilities required to become an Engineering Workspace.

The next phase is to reorganize those capabilities around how engineers naturally think, explore, research, decide, and preserve knowledge.

RFC-002 establishes this evolution.

RFC-002 Part II defines how this evolution will be implemented incrementally across the existing codebase while maintaining backward compatibility and minimizing engineering risk.

# 11. Evolution Strategy

Atlas will evolve through **incremental refactoring**, not a rewrite.

The existing codebase already contains the majority of the required engineering capabilities.

The objective is to reorganize ownership, responsibilities, and user flows while preserving existing infrastructure.

Guiding principle:

> **Refactor the product, not the technology.**

# 20. Backward Compatibility

Atlas must remain functional throughout the migration.

Rules:

Existing APIs continue working.

Existing research remains accessible.

Existing Decision Records remain valid.

GitHub synchronization remains unchanged.

Existing exports remain compatible.

Migration should be invisible to users whenever possible.

Overusing LLMs.

# Closing Statement

RFC-001 defines **why Atlas exists**.

The implementation phase begins after this RFC.

From this point forward, every architectural decision should be evaluated against the Engineering Workspace model rather than the original Research Tool model.

The objective is not to build more AI features.

The objective is to build the engineering workspace that teams can trust throughout the entire lifecycle of software development.
